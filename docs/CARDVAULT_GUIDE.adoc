CardVault is an aesthetic, encrypted-first desktop vault for everything you
carry in a wallet: payment cards, logins, financial accounts, crypto wallets,
identities, documents, memberships, gift cards, physical items, and secure
notes. Every entry is stored as a single AES-256-GCM sealed blob, so the
on-disk database contains no plaintext.

This document is the complete user guide and technical reference. It contains
no personal information and is safe to distribute.

== 1. Overview

.A feature tour
* Ten entry kinds with purpose-built editor templates, tiles, and detail views.
* Everything sensitive is AES-256-GCM encrypted before it touches the database.
* Secrets (PINs, passwords, recovery phrases) are masked until deliberately
  revealed one at a time.
* Live search across entry name, kind, brand, and tags.
* Per-entry tags for grouping and quick filtering.
* Nested folders with a built-in icon library for organising the vault into a
  friendly, navigable tree.
* Drag-and-drop folder re-parenting in the folder manager.
* Entry templates (passport, national ID, driving licence, SSN, …) for
  identity and document kinds, plus fully free-form custom fields on every
  non-card entry.
* Scheduled *automatic encrypted backups* with a retention policy.
* Cross-device *file sync*: an encrypted, opt-in snapshot shared through any
  synced folder (Dropbox, OneDrive, a network drive). No server, no accounts.
* Password-protected export/import for backups and machine transfers.
* One-time CSV export for spreadsheets, plus CSV import.
* KeePass 2 (KDBX 3.x) database import from the settings screen.
* Optional update check against the project's public release feed.
* Changeable master password that re-encrypts the whole vault.
* Configurable idle auto-lock and a SEG7-style "seven-segment" display theme.

== 2. Installing

=== 2.1. Requirements

* Windows x64.
* .NET 8 runtime, or a self-contained publish with no runtime installed.

=== 2.2. From a release

Download the portable single-file build and run the app executable directly.
No install step or administrator rights are required.

=== 2.3. Self-contained publish

[source,console]
----
dotnet publish src/CardVault/CardVault.csproj -c Release -r win-x64 --self-contained true -p:PublishSingleFile=true
----

The output is a single executable under
`src/CardVault/bin/Release/net8.0/win-x64/publish/` that runs on machines
without the .NET runtime.

=== 2.4. Build from source

[source,console]
----
dotnet restore CardVault.slnx
dotnet build CardVault.slnx -c Debug
dotnet run --project src/CardVault/CardVault.csproj
----

== 3. Getting started

=== 3.1. Creating a vault

On first launch you are asked to choose a master password. The password must
be at least 8 characters and include characters from at least *three* of these
four categories: lowercase, uppercase, digits, symbols. Type it twice to
confirmasi.

=== 3.2. The home screen

Entries are shown as a grid of tiles. Card entries render as card faces with
their brand, accent color, and a VFD-style digit display; every other kind
renders as a pocket tile with a kind glyph Good Gé.

Tiles show the entry's name, kind name, tags, and (for cards) the brand label.
Clicking a tile opens the detail view; opening a card face reveals its digits.

=== 3.3. Adding an entry

1. Press the primary action button (the large + button).
2. Pick a kind from the picker.
3. Fill the form. Fields marked *masked* are stored encrypted and rendered as
   dots until you choose to reveal them.
4. Optionally add tags (comma-separated) and notes.
5. Save. The entry is sealed and inserted.

You can also assign the entry to a folder as you create or edit it, using the
*Folder* picker in the form.

=== 3.4. Folder picker

The *Folder* field on the add/edit form places an entry inside an existing
folder. The list is indented to show nesting; choosing "No folder" stores the
entry at the top of your library.

== 5. Folders

Folders group entries into a nested tree with a per-folder icon.

=== 5.1. Creating a folder

From the home sidebar press the folder **+** button (or *Manage folders* → *New
folder*). Give it a name, choose where it lives (*Inside*), and pick an icon from
the library. Folders can be nested arbitrarily deep.

=== 5.2. The sidebar tree

The home screen shows All items plus your folder tree on the left. Selecting a
folder filters the wallet to that folder *and everything inside it* (its whole
subtree); use the chevrons to expand and collapse branches. The count badge
beside each folder shows how many entries live in it (including subfolders).

=== 5.3. Managing folders

*Manage folders* lists the whole tree with edit (rename / re-parent / change
icon) and delete on every row. To move a folder, either edit it and pick its
new *Inside* location, or *drag a row and drop it onto another folder* — drop
it on the dashed strip at the bottom of the list to move it back out to the top
level. Vaults never allow a folder to be dropped into its own subtree (which
would loop), so the tree stays a valid hierarchy. Deleting a folder is safe by
design: its subfolders and entries are *moved one level up* (into the deleted
folder's parent, or the top level for root folders). Nothing is ever deleted
with a folder, and entries only ever end up at the same access path or higher.

=== 5.4. The icon library

Each folder stores a small `icon` key. The editor renders the library as
selectable glyphs grouped by category (folders, essentials, people, security,
finance, home, shopping, travel, media, productivity, communication,
technology, lifestyle). Icons are vector stroke paths drawn at runtime, so they
stay crisp in every theme and size.

=== 5.5. Where folder data lives

Folder names and icons are metadata (not secret) and are stored in the
`folders` table alongside a `folder_id` column on each entry. The encrypted
`secure` blob is untouched.

=== 3.5. Revealing secrets

Sensitive values stay masked. Use the per-item reveal control to temporarily
show a value, and copy it only while revealed. Revelations never persist —
closing the entry re-masks everything.

== 6. Entry kinds

Each kind has its own template. A `kind` string in the database drives the
editor, the tile, and the detail view. The table lists the fields that are
stored in the encrypted payload.

.Entry kinds
[cols="1,3"]
|===
| Kind | Encrypted template fields

| `card` | Holder, Number, Expiry, CVV, Notes, Secrets
| `login` | Website/URL, Username, Password, Notes, Secrets
| `financial` | Institution, Account name, Account number, Routing/BIC, Notes, Secrets
| `crypto` | Network, Wallet address, Seed phrase, Private key, Notes, Secrets
| `identity` | Document type, Full name, Document number, Country, Issue/Expiry, Notes, Secrets
| `document` | Title, Reference, Secure notes, Secrets
| `membership` | Program, Member ID, Tier, Notes, Secrets
| `gift` | Store, Card number, PIN, Balance, Expiry, Notes, Secrets
| `physical` | Item, Location, Combination/Serial, Notes, Secrets
| `note` | Secure notes, Secrets
|===

Cards additionally carry brand information (e.g. `visa`, `amex`, `mastercard`,
custom) and an accent color used for the card-face gradient and digit display.

=== 6.1. Entry templates

Identity and document entries start from a template picker (passport, national
ID, driving licence, SSN, health insurance, residence permit, voter ID,
tax ID). Choosing a template pre-fills the form's labelled fields, and values
are preserved if you switch templates mid-edit. Every non-card entry also
supports free-form rows: add labelled fields with the *Add field* button,
mark anything secret, and rename labels to taste. Field labels and values are
stored inside the encrypted payload, so a custom label only ever exists in
plaintext while you are editing it.

== 7. Tags & search

* *Tags* are comma-separated labels on each entry (e.g. `travel,rewards`).
* The search box filters live as you type, matching name, kind, brand, and
  tags.
* Tags are stored as plaintext columns in the local database (they are not
  secret), so they can be indexed for fast filtering.

== 8. Security model

=== 8.1. Encryption at rest

* *Cipher*: AES-256-GCM (authenticated encryption).
* *Key derivation*: PBKDF2-SHA256 with a random per-vault salt and a high
  iteration count (tens of thousands; the exporter uses the configured
  constant).
* Each entry's payload is a JSON `secure` blob that is `nonce | tag |
  ciphertext`. The nonce is 12 bytes, the GCM tag 16 bytes.
* The master password is never stored — only a derived verification hash.

=== 8.2. Reveal discipline

Nothing sensitive is visible until you ask. Copy-to-clipboard is gated behind
reveal, and details windows are one-at-a-time dialogs so secrets don't linger
on screen.

=== 8.3. Backup

Use *Export → .{ext} file* to produce an encrypted backup that preserves all
kinds, names, tags, and encrypted payloads. Keep backups in a location you
trust and remember the passphrase — there is no recovery without it.

== 9. Export & import

=== 9.1. Encrypted export/import

The `.cvault` format is a compressed envelope of the vault entries and their
encrypted payloads, sealed with a passphrase using the same key derivation as
the vault.

[source,console]
----
# In the UI: Export → export to a .cvault file.
# Import on another machine: Export → import .cvault, then choose a passphrase.
----

Round-trips all ten kinds plus tags and names.

=== 9.2. CSV export

CSV export produces a UTF-8 file with a byte order mark, containing one row
per entry: kind, name, tags, and revealed field/secret labels and values.
Use for spreadsheets when you accept plaintext output. The first three bytes
are `EF BB BF` so Excel detects UTF-8.

=== 9.3. CSV import

CSV import reads the same format back in, mapping each column to an entry and
encrypting the values before storage.

=== 9.4. KeePass import

*Settings → KeePass import* reads a KeePass 2 database (`.kdbx`) and copies its
groups and entries into the vault. The original file is never modified.

For compatibility, the recorder reads KDBX 3.x files with:

* AES-256-CBC encryption with the AES-KDF key transform, password-only
  credentials;
* the Salsa20 "inner random stream" (`\r\n\r\n` EndOfHeader field and the KDBX
  hadhed-block trailer as KeePass/X writes them);
* optional gzip-compressed payloads.

Entries are mapped heuristically:

* *Groups* become folders (nested structure, icons default to `folder`). The
  root group itself is not recreated; its entries land at the top level.
  Recycle Bin and backups groups are imported as ordinary folders.
* An entry is treated as a *card* when it stores a card-like number plus an
  expiry or CVV; the brand is detected from the number prefix (Visa, Mastercard,
  Amex, …). Expiry and holder strings are canonicalized where possible.
* All other entries map to their best-fitting kind:
  `login` when the entry has a username/password or website,
  `document` when it carries custom fields, otherwise `note`.
* Protected values (the KeePass-protected username/password/attributes) are
  decrypted in document order and stored in the matching CardVault fields or as
  `SecretEntry` rows.
* Custom fields are kept as secrets so no information is lost.

Files that are not recognizable KeePass 2 vaults, use unsupported ciphers or
inner-stream algorithms, fail their header-hash check, or reject the entered
password are reported clearly and left untouched.

== 10. Automatic backups

In *Settings → Automatic backups* you can ask the vault to write an encrypted
backup on a schedule (daily, weekly, monthly) and keep only the newest N files
(7, 14, 30, or 60). A *Back up now* button forces an immediate run.

Unlike the interactive export (which prompts for a passphrase), automatic
backups reuse your *master key*, so no passphrase prompt can appear
unattended. The `.cvault` file records the same KDF salt and iteration count
as your vault, which means the file can still be restored on any CardVault
installation with your normal master password. Old files beyond the retention
window are deleted after each successful backup.

Preference keys (`backup_folder`, `backup_cadence`, `backup_retain`,
`backup_last`) live in the vault's `meta` table. The timer only runs while the
vault is unlocked.

== 11. Sync across devices

CardVault sync is an *opt-in, encrypted, peer-to-peer* feature with no server
and no accounts. Both machines point at the *same shared folder* — a Dropbox
or OneDrive folder, a network drive (SMB/NAS), or any folder that is synced by
another tool — and the app exchanges one encrypted snapshot file there.

=== 11.1. Setting it up

1. In *Settings → Sync across devices* turn on *Enable file sync*.
2. Choose a shared folder that both devices can see (and that syncs between
   them if it isn't already a network folder).
3. Press *Sync now*. Once the first device has written a snapshot, the second
   device adopts the sync key automatically the next time it is unlocked.
4. Both devices must unlock with the *same master password* — the snapshot is
   encrypted with a key derived from it.

There is no re-enabling ceremony: after the first sync, the vault exchanges
changes on its own every few minutes while unlocked, and immediately after
unlocking. *Sync now* in Settings gives you a manual pull-push.

=== 11.2. What sync does

The snapshot contains every entry (name, kind, brand, tags, folder
assignment, timestamps, and the encrypted payloads), every folder, and a list
of *tombstones* (deletions). On each run the app performs a last-writer-wins
merge per item using each item's modification time: the newer copy — local or
remote — wins, and the merged result is written back to the shared file. If
the same item was edited on both devices, the newest edit survives; editing the
same item on two devices at the same time is the one genuinely conflicting
case (the newer timestamp wins).

Deletions are carried as tombstones so an offline device does not quietly
resurrect something that was deleted elsewhere. Tombstones older than a year
are pruned.

=== 11.3. Security

* The snapshot file (``*{appname}-sync.cvsync``) is sealed with AES-256-GCM
  under a key derived from your master password plus a *dedicated random sync
  salt* that the first device generates. The salt is baked into the file's
  header, so every device derives the same key with the same password — your
  vault's own KDF parameters never need to match.
* The sync key lives only in memory, is derived when you unlock, and is zeroed
  the moment the vault locks. While locked, no syncing happens.
* If a snapshot cannot be decrypted (for example the other device's master
  password differs), CardVault refuses to touch the shared file, so a foreign
  snapshot is never overwritten or destroyed.

Meta keys involved: `sync_folder`, `sync_enabled`, `sync_last`,
`sync_salt`, `sync_iter`, `sync_device`, and `sync_tombstones`.

== 12. Settings

* *Change master password*: requires the current password; re-encrypts every
  entry under the new derived key.
* *Auto-lock*: lock the vault after a configurable idle timeout.
* *Automatic backups*: schedule encrypted backups with retention (see
  <<Automatic backups>>).
* *Sync across devices*: enable and manage encrypted file sync (see
  <<Sync across devices>>).
* *Themes*: Atelier (default), and Readout with the SEG7 seven-segment
  character display for the card-face digits.
* *Update check*: optional, checks the public release feed. It is the only
  network call the app makes — file sync touches only your shared folder.

== 13. How CardVault works under the hood

=== 13.1. Storage

The vault is a single SQLite database file located in the per-user
application-data directory. Three core tables:

* `meta` — key/value store: `kdf_salt`, `kdf_iter`, `master_hash`, `version`,
  plus application metadata such as theme and lock timeout, auto-backup
  preferences (`backup_folder`, `backup_cadence`, `backup_retain`,
  `backup_last`), and sync state (`sync_folder`, `sync_enabled`, `sync_last`,
  `sync_salt`, `sync_iter`, `sync_device`, `sync_tombstones`).
* `entries` — one row per entry: `id`, `kind`, `name`, `brand`, `accent`,
  `tags`, `folder_id`, `secure` (the encrypted `nonce|tag|ciphertext` blob),
  `created_at`, `updated_at`.
* `folders` — one row per folder: `id`, `parent_id`, `name`, `icon`,
  `created_at`, `updated_at`. An empty `parent_id` means top level; an empty
  `folder_id` on an entry means no folder.

=== 13.2. Migration

Opening a database created by an older schema detects and migrates it:

* A legacy `cards` table is migrated into the unified `entries` table with
  `kind = 'card'`.
* Missing columns (e.g. `tags`, `folder_id`) are added to existing entries
  tables so old vaults keep working without data loss.

There is no plaintext in either table — the `secure` blob stays opaque.

=== 13.3. Key derivation & master verification

`DeriveKey(passphrase, salt, iterations)` = PBKDF2-SHA256. The derived key
unlocks/encrypts entries; a separate derived value stored in `master_hash`
verifies the passphrase without storing it. On change, all `secure` blobs are
re-sealed with the new key.

== 15. Troubleshooting

*Forgot the master password?* There is no recovery path by design. Use a
current backup.
*Vault won't open?* Confirm the file path points at a valid vault; corrupted
files error out and are left untouched.
*CSV looks mangled in Excel?* The export writes UTF-8 with BOM; if your
environment shows mojibake, re-import via the app's CSV importer instead.
*Sync shows "Could not decrypt the sync snapshot"?* The shared folder contains
a snapshot written with a different master password. Unlock both devices with
the same password, or — if you truly want to start over — remove
`cardvault-sync.cvsync` from the shared folder on all devices first.
*Sync sometimes needs two cycles?* Folder deletions can leave an entry's
folder assignment one merge behind while the surviving copy is re-parented.
This is cosmetic and self-corrects on the next sync.
